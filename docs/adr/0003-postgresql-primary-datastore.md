# ADR 0003: PostgreSQL as the primary datastore (with pgvector)

- **Status:** accepted
- **Date:** 2026-08-22
- **Deciders:** Lead Architect

## Context

Athena's data is fundamentally relational: papers ↔ authors ↔ topics ↔
citations with unique constraints needed for deduplication (DOI/arXiv ID
uniqueness), plus provenance rows per source. We also need to store raw
provider payloads, user data, AI artifacts, a job queue, and — later — vector
embeddings and full-text search. Operational surface should stay small for an
MVP team.

## Decision

PostgreSQL 16 is the single system of record. The local/production image is
`pgvector/pgvector:pg16` so the `vector` extension is available when the RAG
phase lands.

Rules:

- Core queryable attributes are real columns with constraints; **JSONB is
  reserved** for provider raw payloads, sync cursors, and flexible settings.
- Primary keys are UUIDs generated by the application as **UUIDv7**
  (time-ordered → index locality, sortable) with `gen_random_uuid()` as DB-side
  fallback.
- `citext` for emails and DOIs; native enums for closed sets
  (`explanation_level`, `oa_status`, `publication_type`, job status).
- All timestamps are `timestamptz` (UTC).
- Soft deletes only where required (`deleted_at`); ingestion data prefers
  idempotent upsert over delete.

The baseline schema lives in `backend/migrations/000001_init_schema.up.sql`
and is documented in `docs/database/schema.md`.

## Alternatives considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| MySQL 8 | Ubiquitous | Weaker JSONB/FTS/pgvector story | Postgres strictly better fit here |
| MongoDB | Flexible docs | Dedup/citation integrity needs joins & transactions anyway | Relational model fits bibliographic graph |
| Dedicated vector DB (Qdrant/Milvus/Pinecone) now | Best-of-breed ANN ops | Extra infra, sync burden, premature at MVP scale | pgvector first; port boundary keeps swap cheap (see ADR-0005) |
| SQLite | Zero-ops | Concurrent writer limits, FTS/vector gaps at scale | Not viable for multi-worker ingestion |

## Consequences

**Positive:**

- One backup/monitoring/failover surface; transactional consistency across
  paper writes *and* job enqueues (enables ADR-0006).
- Rich indexing (GIN on tsvector/trigram, partial indexes, HNSW) in one place.

**Negative / risks:**

- Vertical scaling ceiling eventually → documented path: read replicas for the
  API, then extract search engine (ADR-0005) and/or archive cold citation
  edges.
- Changing embedding model changes vector dimensionality → requires a versioned
  embeddings table/column migration; designed for from day one (`chunk_embeddings`
  keyed by `(chunk_id, model_id)`).

**Follow-ups:**

- [ ] Phase 1: connection pooling via pgxpool; statement timeouts set per role.
